## 1. Context (verified facts, 2026-07-02)

- Monorepo: `nearby-admin` (admin panel, FastAPI + React/Mantine) and `nearby-app` (public app, FastAPI + React/Leaflet). Both share ONE production Postgres (RDS `nearby-admin-db`).
- Scale: ~31 published POIs in prod. Data is manually curated (client: Rhonda). The dataset is the business asset; the apps are replaceable views.
- Main table `points_of_interest`: 9 POI types, ~142 columns, 54 of them JSONB. Subtype tables: `businesses` (1 real column), `parks` (1), `trails` (22), `events` (37).
- Field registry `shared/poi_fields.json` (213 entries, generated by `scripts/gen_poi_registry.py`): drives the public serializer, frontend rendering, SEO, and contract tests. It is good; keep it.
- Both backends contain a full COPY-PASTED duplicate of the POI ORM. Two prod incidents trace to this: `sponsor_logo` enum drift (public 500s) and the `m_payphone` in-place column rename (~4-5 min outage during rolling deploy).
- RDS `nearby-admin-db`: db.t4g.micro, single-AZ, **backup retention 1 day**, **deletion protection OFF**, Postgres 17.9.
- Second RDS instance `nearby-admin-db-public-dev`: db.m5.large, **publicly accessible**, not referenced by prod SSM params (`database-url` and `forms-database-url` both point at the main instance). Unaccounted ~$125+/mo and a security exposure.
- No audit trail / revision history / soft delete anywhere.
- CI auto-deploy is BROKEN since the GitHub org move (TesslateAI -> NearbyNearby). Deploys are currently manual.
- Cloudflare -> ALB is plain HTTP on port 80 (origin unencrypted).
- Nearby feature filters only by 5 type pills + search. None of the 54 JSONB attribute fields power any filter (data is display-only today).
- POI-to-POI links exist in THREE mechanisms: the proper `poi_relationships` edge table, real FKs on events, and untyped UUID arrays inside JSONB (`service_locations`, `locally_found_at`, `associated_trails`, `membership_passes`, `vendor_poi_links`, `organization_memberships`). The JSONB arrays have no FK integrity (ghost refs on delete).
- Geometry stranded in JSON: `parking_locations`, `toilet_locations`, `playground_locations`, `payphone_locations`, trail `access_points`, `trailhead_location`. PostGIS cannot query these.
- Duplicate representations: photos (`photos` JSONB + `featured_image` + `gallery_photos` + `images` table), contact (`contact_info` JSONB + `main_contact_*` + top-level phone/email), payments (`payment_methods` + `amenities.payment_methods`).
  - NOT a duplicate: `ideal_for` vs `ideal_for_key`. `ideal_for_key` is the deliberate "featured top-3" picker (Business+Event). Keep both; document.
- 5+ `_deprecated_*` columns still in the schema (data already migrated off them).
- `embedding vector(768)` exists in the DB but is intentionally unmapped on the app ORM (documented gotcha; keep unmapped, add a model comment).
- Card serializer `_CARD_SCHEMA_KEYS` (hand-maintained) silently drops 10 registry `card:true` fields (`difficulty`, `length_text`, `start_datetime`, `icon_*` x4, `is_sponsor`, `main_image`). No test guards this.
- Validation inconsistent: CHECK constraints exist for alcohol/parking/listing_type/publication_status/sponsor_level, but `status`, `event_status`, `cost`, `gift_cards`, `drone_usage`, `hunting_fishing_allowed`, `fishing_allowed` are unconstrained strings.
- Disaster hub today = `DISASTER_HUBS` POI type + `is_disaster_hub` boolean (two conflicting representations) + 2 admin-only free-text fields. No capabilities, capacity, status, or freshness.
- 4 of 9 POI types (JOBS, VOLUNTEER_OPPORTUNITIES, YOUTH_ACTIVITIES, DISASTER_HUBS) have no subtype table and no type-specific fields; they are categories wearing a type costume.

## 2. Goals

1. Data cannot be silently lost or corrupted (durability + auditability).
2. Structural drift between the two backends becomes impossible.
3. The schema's integrity bugs are fixed while migrations are cheap (~31 rows).
4. Collected attribute data becomes actionable (facet filters in the Nearby feature).
5. Ready for GIS (real geometries) and a credible disaster-recovery-hub feature.
6. Net simpler system at the end, not a fancier one.

## 3. Explicitly REJECTED approaches (do not re-propose)

- **EAV attribute tables** (`attribute_definitions` + `poi_attribute_values`): rejected. JSONB containment queries with GIN indexes deliver faceting with zero schema migration. EAV adds joins, breaks the registry's `getattr` serializer, and buys nothing at this scale.
- **Normalizing `hours` into rows**: rejected. The JSONB handles seasonal/dawn-dusk/holidays; Python filtering of the small nearby candidate set is fine for years. Revisit only if a whole-database "open now" query is ever needed.
- **OSM-style free key=value tagging**: rejected. Would destroy the typed audience/tier/PII control the registry provides. Take OSM's geometry model and controlled vocabularies (opening_hours, wheelchair, amenity) as value standards only. Note: OSM *data* is ODbL share-alike; never bulk-import it into this proprietary DB. Government open data (usually public domain) is fine.
- **Headless CMS migration** (Directus/Payload): rejected for now. The admin's bespoke logic (venue inheritance, recurring events, conditional type sections) exceeds CMS customization sweet spots. Lesson retained: stop hand-building commodity features; build the simple version (e.g. JSON-snapshot revisions, not an audit framework).
- **Multi-AZ / multi-region now**: rejected. The static disaster fallback (Phase 4) buys more resilience per dollar. Multi-AZ only if/when disaster-hub becomes a funded mandate.
- **Full rewrite / microservices**: rejected. Direction is FEWER deployables.

### Task 0.2: Decommission the public dev RDS instance

## PHASE 1: Make data un-breakable (~1-2 weeks)

### Task 1.1: POI revisions (audit trail)
- New table `poi_revisions`: `id`, `poi_id` (indexed, NOT a CASCADE FK: revisions must survive POI deletion), `action` (create/update/delete), `snapshot` JSONB (full serialized POI incl. subtype + categories + relationship summary), `user_id`, `created_at`.
- Write on every admin POI create/update/delete (including autosave path, `app/utils/autosave_whitelist.py` flow). Keep it dumb: serialize and insert.
- v1 needs NO UI. Optional v2: admin endpoint to list revisions + restore one.
- Verify: tests proving a revision row per mutation; deleting a POI leaves its revisions.

### Task 1.2: Single shared ORM
- Move the SQLAlchemy models into `shared/models/` (poi, category, image, etc.); both backends import from there. Delete both duplicated copies. Alembic stays in nearby-admin only (admin owns the schema).
- Watch: geoalchemy2 dependency in nearby-app image; the app's deliberate non-mapping of `embedding` (keep it unmapped in the shared model; add a comment explaining why); Docker build contexts must include `shared/` (nearby-app's already does for the registry mirror problem, confirm admin's).
- Verify: both test suites green; both images build; the two image-type enums are now ONE definition.

### Task 1.3: Drop deprecated columns
- Drop `_deprecated_public_transit_info`, `_deprecated_key_facilities`, `_deprecated_holiday_hours`, `_deprecated_payphone_location`, `_deprecated_primary_display_category` (+ any others matching `_deprecated_%`).
- FIRST verify in prod (read-only query) that migrated destinations hold the data (e.g. `hours->'holidays'`, `payphone_locations`). Snapshot, migrate.

### Task 1.4: Card schema drift
- Decide field-by-field whether the 10 registry `card:true` fields missing from `_CARD_SCHEMA_KEYS` belong on cards (recommend adding: `difficulty`, `length_text`, `start_datetime`, `icon_*`; these power card badges). Align the set, update `NearbyCard.jsx` where it makes sense.
- Add test: `_CARD_SCHEMA_KEYS` ⊇ {registry entries with `card==true` and `audience==public`} (modulo documented exclusions). No more silent drops.

## PHASE 2: Model fixes that pay (~2-4 weeks; each task independently shippable)

### Task 2.1: Kill ghost refs (referential integrity)
- Migrate every JSONB UUID-array link into `poi_relationships` with new `relationship_type` values: `service_location`, `locally_found_at`, `associated_trail`, `membership_pass`, `vendor`, `organization_membership`.
- Expand/contract: backfill edge rows from JSONB -> update admin form read/write + app serializer/registry (`source` changes) -> later release drops the JSONB columns.
- Add proper FK behavior so deleting a POI removes its edges. Registry regen + contract tests after each step.
- Verify: create/link/delete flows in admin; public pages render linked POIs; no orphan references possible.

### Task 2.2: Facet filters in the Nearby feature (the product win)
- NO schema change. Pick the facet set with the user (suggest: pet-friendly, restrooms, wheelchair accessible, free wifi, playground, payment methods, alcohol, kid-friendly/ideal_for).
- Add GIN indexes (`jsonb_path_ops`) on the chosen JSONB columns (migration, cheap).
- Backend: filter params on `/api/pois/{id}/nearby` (and hybrid-search) translating to `col @> '["value"]'` (booleans use the `icon_*` columns).
- Frontend: filter chips/drawer in `NearbySection.jsx` alongside the existing type pills.
- Verify: integration tests per facet; manual check that "pet friendly" + 5 miles returns correct POIs.

### Task 2.3: `poi_points` (geometry out of JSON)
- New table: `id`, `poi_id` FK CASCADE, `kind` (enum: parking, restroom, playground, payphone, trailhead, access_point), `geom` POINT 4326 (GIST index), `meta` JSONB (kind-specific extras like playground types/surfaces or descriptions).
- Backfill from `parking_locations`, `toilet_locations`, `playground_locations`, `payphone_locations`, trail `access_points` + `trailhead_location`.
- Expand/contract; admin map-pin UIs write to it; app reads from it; JSONB columns dropped in a later release. Registry entries updated.
- Verify: "nearest restroom" style query works in SQL; admin pin add/move/delete round-trips.

### Task 2.4: Real geometries for GIS
- Nullable `geom_line` (LINESTRING, 4326) and `geom_area` (POLYGON, 4326) on `points_of_interest`, GIST-indexed. Trails may get lines; parks may get areas. Everything keeps its POINT.
- Derive trail length (`ST_Length(geography)`) when a line exists; `length_text` remains the display fallback.
- Admin drawing UI (Leaflet draw) is a SEPARATE later task; ship schema + API + registry first so import scripts can populate geometries.
- Verify: a manually inserted test line yields correct computed miles; `ST_Contains(park.geom_area, trail.location)` works.

### Task 2.5: One representation per concept
- Photos: the `images` table wins. Backfill any URLs living only in `photos`/`featured_image`/`gallery_photos` into `images`; make admin+app read exclusively from `images`; drop the three columns (later release). Keep a `featured` flag or image_type ordering for the hero image.
- Contact: keep top-level public `phone_number`/`email`/`website_url`. Keep `main_contact_*` columns (admin-only PII). Migrate anything inside `contact_info` JSONB into those and drop `contact_info`.
- Payments: `payment_methods` column wins; migrate any `amenities.payment_methods` data in; stop writing it.
- Do NOT touch `ideal_for`/`ideal_for_key` (intentional pair).
- Verify: PII contract test still green (this is the leak surface); public pages unchanged.

### Task 2.6: Validation hardening
- CHECK constraints (mirroring the existing pattern) for: `status`, `event_status`, `gift_cards`, `drone_usage`, `hunting_fishing_allowed`, `fishing_allowed`. First run read-only prod queries to catch existing out-of-vocab values; clean via migration.
- `cost` stays a display string for now (numeric min/max split DEFERRED unless price faceting is requested).

### Task 2.7: Type-system cleanup (needs product sign-off)
- Read-only prod query: POI count per type. **STOP AND ASK** with the counts before changing anything.
- Drop `businesses` and `parks` subtype tables (move `price_range`, `drone_usage_policy` to the base table). Keep `trails`/`events`.
- Collapse `YOUTH_ACTIVITIES` into a category (migrate any existing rows to BUSINESS/SERVICES + category). If `JOBS`/`VOLUNTEER_OPPORTUNITIES` have zero prod rows and no roadmap commitment, remove them; else leave until a product decision.
- `DISASTER_HUBS` type: leave until Task 4.1 replaces it.
- Enum removal is expand/contract too: stop offering the type in admin first, migrate rows, then remove the enum value with both apps deployed in the right order.

## PHASE 4: Strategic features (after Phase 2; Phase 3 not a prerequisite)

### Task 4.1: Disaster hub profile
- New table `disaster_hub_profiles`: `poi_id` PK/FK, `capabilities` text[] (vocab: water, power, charging, shelter, food, medical, comms, fuel), `capacity_notes`, `operational_status` (enum: operational, limited, closed, unknown), `last_verified_at` timestamptz, `verified_by`, `public_instructions` text.
- `is_disaster_hub` becomes derived (profile exists); keep the column synced during transition, drop later. Retire the `DISASTER_HUBS` POI type (hubs are businesses/parks/etc. WITH a profile).
- Admin: a Disaster Hub section with a one-tap "verify now" (stamps `last_verified_at`). Public: hub badge + capabilities + freshness ("verified 2h ago"; stale >72h shows a warning).
- Freshness is the point: stale disaster info is worse than none.

### Task 4.2: Static disaster fallback (must not depend on the live stack)
- On any hub profile change (and daily), export all hub data as static JSON + a pre-rendered, low-bandwidth HTML page (inline CSS, no JS required) + printable version to S3/CloudFront at a stable URL (e.g. `nearbynearby.com/emergency` routed to CloudFront).
- This page must remain correct and reachable if the entire backend, database, and VPC are down. Test exactly that (stop the ECS service in a maintenance window or verify path independence by inspection).

### Task 4.3: GIS increments (in order, each optional until needed)
1. Admin Leaflet-draw UI for trail lines / park polygons (writes Task 2.4 columns).
2. Computed lengths + trail-in-park containment validation surfaced in admin.
3. Bulk import framework for government open data (state park boundaries, trail lines; public domain only, never OSM/ODbL). This is the growth path beyond manual entry.
4. Vector tiles (Martin/pg_tileserv) ONLY if map performance ever demands it.

## 5. Decision triggers (revisit the plan if...)

- Field churn stays weekly for months -> build registry-driven admin form generation (new field cost drops to ~0).
- POI count must grow 100x via imports -> pull typed `text[]` conversion + import pipeline forward.
- Disaster-hub becomes funded/mandated -> add Multi-AZ and real SLOs (static fallback stays first line).
- A second tenant/client appears -> revisit headless CMS and multi-tenancy before building more admin surface.
